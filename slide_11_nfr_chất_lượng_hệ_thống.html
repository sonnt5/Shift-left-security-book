Non‑Functional Requirements (NFR) & Chất lượng hệ thống

Khái niệm & vai trò

NFR là “cách hệ thống vận hành & được cảm nhận”

  • NFR = thuộc tính chất lượng: hiệu năng, bảo mật, khả dụng, quan sát/giám sát, tuân thủ, mở rộng…
  • Không đứng ngoài quy trình: NFR được dệt vào artefacts, QA points & milestones → phải có work products kiểm chứng.
  • Tư duy: “viết được • đo được • kiểm thử được” thay cho khẩu hiệu.
Từ yêu cầu đến bằng chứng

Chuỗi Task set → Work products → QA → Milestones

  • Mỗi NFR cần: metric (p95 latency, error‑rate…), target, workload/bối cảnh, cách đo.
  • Liên kết truy vết hai chiều: NFR → ADR/Thiết kế → Code/Cấu hình → Test/Monitoring → Evidence.
  • Qua cổng (SDR/Bug Bar/FSR) dựa trên evidence đã tích lũy trong Evidence Store.
Các NFR trọng yếu & ví dụ

Performance • Security • Observability • Availability • Compliance

  • Hiệu năng: mục tiêu theo phân vị (p90/p95/p99) dưới tải thực; VD: đọc hồ sơ ≤ 300 ms @p95, 200 RPS; thiết kế: cache theo patient_id, index DB, tách đọc/ghi.
  • Bảo mật: yêu cầu kiểm soát đo được cho danh tính & truy cập và bảo vệ dữ liệu. Ví dụ cách viết yêu cầu: “100% endpoint nhạy cảm chỉ chấp nhận yêu cầu có danh tính hợp lệ; phiên/credential hết hạn ≤ 60 phút; truy cập mặc định deny‑by‑default và cấp theo vai trò; 100% hành động quan trọng đều được audit.” Với dữ liệu nhạy cảm: “100% PII lưu trữ phải được mã hoá at‑rest bằng thuật toán chấp nhận công nghiệp; khoá do KMS quản lý; rotation ≤ 90 ngày.”
  • Quan sát: logs/metrics/traces có correlation IDs; VD: audit event = identity+time+action+resource+outcome, 95% truy vấn audit ≤ 5 s.
  • Khả dụng: SLO 99.9%, RTO 15′, RPO 5′; multi‑AZ, auto‑failover; runbook sự cố kiểm thử hàng quý.
  • Tuân thủ: retention 180 ngày cho audit log; data masking môi trường test; consent log; kiểm toán định kỳ.

Sơ đồ — Biến NFR thành bằng chứng

Forward: hiện thực hoá NFR thành thiết kế → code → kiểm thử/giám sát; Backward: truy nguyên từ test/log về NFR nguồn.
Giải thích sơ đồ:
  • NFR (tiêu đề rõ ràng) nên viết dạng: Khi [điều kiện/workload], hệ thống phải [mục tiêu + metric] trong [ràng buộc/tài nguyên]. Ví dụ: “Đọc hồ sơ p95 ≤ 300 ms ở 200 RPS.”
  • ADR/Thiết kế ghi lý do tin rằng mục tiêu đạt được (kiến trúc, ràng buộc, ngân sách hiệu năng).
  • Code/Config hiện thực hoá quyết định (chỉ mục DB, cache, giới hạn kết nối, flags…).
  • Test/Monitor biến mục tiêu thành bài test + dashboard; kết quả, báo cáo, chữ ký… gom vào Evidence Store.
  • Backward trace: khi test/log cảnh báo, có thể truy ngược về NFR & ADR nào cần điều chỉnh.
  • Gates: SDR/Bug Bar/FSR đọc đúng evidence từ store để ra quyết định Go/No‑Go/Risk Accepted.

Sơ đồ — Performance budget (đọc hồ sơ ≤ 300 ms @p95)

Ngân sách phân rã theo tầng giúp kiểm soát ngay từ thiết kế & review.
Giải thích sơ đồ:
  • Tổng ngân sách = 300 ms @p95; các đoạn (API/DB/Cache/Khác) cộng lại bằng tổng.
  • Thiết lập: xác định workload (200 RPS, Zipfian), timeout, retry; phân bổ ngân sách theo điểm nghẽn dự báo.
  • Giám sát: mỗi phân đoạn có metric tương ứng (latency API, query time DB, hit‑ratio cache); cảnh báo khi vượt 80% ngân sách.
  • Ứng phó: nếu DB vượt ngân sách → bổ sung index, tối ưu truy vấn, đẩy đọc sang cache; nếu API vượt → cắt đồng bộ, dùng hàng đợi/batch.
  • Đóng mốc: milestone chỉ “đóng” khi số đo thực tế đạt mục tiêu liên tục trong thời gian quan sát (ví dụ 7 ngày).

Case Study — e‑Clinic

Hai mục tiêu then chốt

  • SLA đọc hồ sơ ≤ 300 ms (p95): profiling luồng đọc; covering index; cache theo bệnh nhân; kiểm thử tải 200 RPS; dashboard p50/p95/p99 theo endpoint. Work products: ADR “Read‑Path Budget”, kịch bản k6/JMeter, báo cáo test; QA: Performance Readiness Review; Milestone: đóng khi p95 ≤ 300 ms ổn định 7 ngày.
  • Audit phải queryable: định nghĩa audit event schema (identity, time, action, resource, outcome, request_id); structured logging + retention 180 ngày; index (patient_id, action, time); test truy vấn “ai‑đã‑xem‑bệnh‑án‑X 10:30–10:35” ≤ 5 s. Work products: schema + index + truy vấn mẫu + báo cáo; QA: review format log trong SDR; Milestone: dashboard SLA truy vấn đạt.
Gắn vào nhịp SDLC & các “ô dù”: SQA định nghĩa Definition of Done; risk management theo dõi risk exposure; SCM quản trị cấu hình (IaC, policy, feature flags); reviews (SDR/FTR) kiểm tra evidence trước mốc.
