Planning — phạm vi & rủi ro

Goal

Biến “muốn làm” → kế hoạch thực thi & kiểm soát

  • Xác lập scope, phân rã WBS, ước lượng (size/effort/cost), lịch (mốc & nguồn lực).
  • Chuẩn bị kế hoạch chất lượng: SQA • Test • Config • Security cùng QA points & gates.
  • Đầu ra: Project Plan nhất quán với artefacts Communication (SRS/use case/NFR) và có risk plan kèm theo.
Khung theo Process Structure: Communication → Planning → Modeling → Construction → Deployment.
WBS

Phân rã để dễ ước lượng & kiểm soát

  • Mỗi work package có: (1) work product hữu hình, (2) tiêu chí chấp nhận/QA point, (3) effort/duration, (4) phụ thuộc, (5) owner.
  • Phân rã theo 5 framework activities; ví dụ: Modeling→ ADR, data model, API contract. Construction→ Booking API endpoints, test, hardening.
  • Traceability: yêu cầu → công việc → mốc; đo tiến độ theo artefact.

Sơ đồ — Cây WBS (rút gọn)

Each Work Package (WP) is deliverable‑based with clear acceptance criteria, a single owner, explicit dependencies, and measurable DoD. Lines are split with a connector bar to avoid overlap.
WBS — Notes

Guidelines & tips (keywords in English)

  • 100% Rule: tổng các con của một node phải bao phủ 100% scope của node đó, không hơn không kém.
  • MECE (Mutually Exclusive, Collectively Exhaustive): tránh chồng lấn giữa các work packages.
  • Work Package (WP) sizing: nên 1–5 ngày; nếu >5 ngày thì tiếp tục phân rã.
  • Deliverable‑based WBS: tổ chức theo deliverables (ADR, API contract, endpoints, tests) thay vì chỉ theo pha.
  • Entry/Exit criteria • DoD: mỗi WP phải có artefact, acceptance criteria, QA point rõ ràng.
  • Traceability: map requirement → WP → milestone/gate để theo dõi tiến độ và kiểm soát phạm vi.
  • Progressive elaboration: tinh chỉnh WBS theo từng increment khi thông tin mới xuất hiện.
Estimation & Schedule

Đa góc nhìn & gắn driver

  • Kết hợp analogy, expert judgment, bottom‑up từ work packages, hoặc 3‑điểm/PERT (o, m, p).
  • E[effort] ≈ (o + 4m + p) / 6 · (beta) → chuyển thành lịch qua phụ thuộc, resource, buffer.
  • Lịch thể hiện milestones & gates: M1 Scope Freeze • M3 Design Freeze + SDR • M4 Feature Complete + Bug Bar • FSR.
  • Cost of quality: review kỹ thuật, SAST/DAST, hardening, evidence cho cổng.
Formulas

Quick guide (keywords in English)

  • PERT expected duration: E = (O + 4M + P) / 6; StdDev: σ = (P − O) / 6; Variance: σ² = ((P − O)/6)².
  • Critical Path / Slack: Slack = LS − ES = LF − EF. Tasks on the critical path have Slack = 0.
  • Earned Value: SPI = EV / PV, CPI = EV / AC, EAC ≈ BAC / CPI, ETC = EAC − AC.
  • Risk Exposure: RE = Probability × Impact (qualitative or quantitative); track via risk burn‑down or heat map.
  • Bug Bar: gate closes only when Open[Critical/High] ≤ threshold (e.g., 0/0) and key tests pass.
Tips: Use three‑point estimates for high‑uncertainty WPs; convert effort to duration via resource calendars; keep assumptions alongside each estimate for later re‑estimation.

Risk management

Động cơ điều hướng kế hoạch

  • Identify (kỹ thuật, tổ chức, phụ thuộc, lịch/chi phí, an toàn & tuân thủ).
  • Analyze (xác suất × tác động → exposure; ghi triggers).
  • Plan (avoid/mitigate/transfer/accept) → thêm tasks vào WBS: mock, benchmark, rollback.
  • Track/Control theo increment; cập nhật exposure, lịch, nguồn lực qua risk register.

Sơ đồ — Vòng lặp rủi ro liên tục

Risk register: mô tả, nguyên nhân, exposure, chiến lược, tasks/owner/due, triggers, trạng thái.
Metrics

Bộ đo tiến độ & chất lượng (gắn vào gates)

Progress
  • Burn‑down/Burn‑up
  • EV: SPI = BCWP/BCWS, CPI = BCWP/ACWP
  • % artefact qua QA points; % mốc đúng hạn
Quality
  • Defect trend & removal efficiency
  • Escaped defects • Test coverage
  • Bug Bar: Critical/High còn mở
NFR
  • p95 latency / endpoint • Error rate
  • SLO/SLA availability
  • Audit query time • MTTR
Policy/Gates
  • M3 đóng khi đủ SDR
  • M4 đóng khi đạt Bug Bar
  • FSR kiểm chứng NFR & tuân thủ
Incremental Control

Quản trị rủi ro liên tục theo increment

  • Mỗi iteration cập nhật giả định, re‑estimate phần còn lại, điều chỉnh risk plan.
  • Vẽ risk burn‑down/heat map để thấy exposure giảm hay dồn cục.
  • Thông tin mới (vd. benchmark tệ) ⇒ kích hoạt change control: update WBS/lịch/nguồn lực, ghi tác động vào traceability.
Case Study

Phụ thuộc API bảo hiểm (BHYT)

  • Risk: dịch vụ BHYT không ổn định/thay đổi hợp đồng API → fail xác minh quyền lợi.
  • Triggers: 5xx/timeout > 2%/giờ; schema đổi không báo; p95 > 2s.
  • Mitigation (thêm vào WBS): Mock + contract tests; outbox & retry/backoff; fallback thủ công; dashboard quan sát; mTLS + allowlist; đàm phán SLA.
  • Theo dõi: p95 tới BHYT, tỉ lệ retry, số lần fallback; chaos test trước Go‑Live; “risk accepted” khi còn thấp & có owner + deadline.

Quality & Security

Kế hoạch chất lượng & bảo mật nằm ngay trong Planning

  • Lập Test Plan, Security Plan, Configuration Plan — quy định ai–làm gì–khi nào.
  • Tự động hoá: CI/CD, SAST/DAST, SBOM; lưu bằng chứng tại Evidence Store.
  • Definition of Done cho từng work package = artefact + QA point + traceability.
Kết luận thực hành: Biến rủi ro lớn thành công việc cụ thể trong WBS, gắn metrics vào gate, cập nhật theo increment để điều khiển lộ trình thay vì bị lộ trình kéo đi.
